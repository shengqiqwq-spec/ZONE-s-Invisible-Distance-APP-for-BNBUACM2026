一、作品说明

1.1 选题与理由

本届四道选题中，我们选择了 The Invisible Distance，理由有三：

  • 可量化。「哪条路更近」是一个能用数字回答的问题。我们把它拆成「平地距离 + 楼层高差 × 基准时间」， 每一项都有明确的计量单位，结论可以被验算，而不是靠形容词。
  • 切口小、场景熟悉。不做整个校园导航，只做图书馆 → V27 雨果楼这一段。这一段同时具备「近路带台阶」与 「远路全平路」两个选项，是能一句话说清、又足够说明问题的最小完整案例。
  • 结论会反转——而且实测真的反转了我们自己的预设。项目最初按地图估算认为「台阶路 A 更短」；2026-10-12 用运动 App 实测推翻： A 实际 537 m，比户外平路 B（470 m）更长。真正的反转藏在「距离最短」与「代价最低」的分离——台阶旁的坡道、沿途补给的差异， 以及一条需要楼梯/电梯的更短室内路线（采集中）。同一组数据，对不同的人答案不同——这正是赛题想问的东西。

1.2 核心洞察

命题：地图软件给出的「最近」，衡量的是平面距离；而人走一段路真正付出的代价，还包括 楼层的垂直高差、台阶这种物理门槛，以及你当时带着什么东西、身体处于什么状态。
结论：当这些被地图忽略的变量足够大时，「最短的路」和「最近的路」就会分道扬镳——这就是那条看不见的距离。

1.3 作品内容与交互

作品是一个可在任意浏览器直接打开的单文件网页（无需服务器、无需联网），打开即见校园真实地图。主要交互：

两条路线叠图对比路线 A 与路线 B 同时画在地图上，切换视角时强调对应那条让「近路」和「安全路」的空间差异肉眼可见

1.4 量化模型

把「走一段路有多累」写成一个可计算的式子，是整个作品的技术核心：

真实代价 = 平地距离 + 楼层高差 × 基准时间

平地距离   ：沿 OSM 实际步道累加（米）
楼层高差   ：上 N 层取正、下 N 层取负，只算楼层差、不数单个台阶
基准时间   ：每层楼梯约 1 分钟（上下同）
拖行李惩罚 ：涉及下坡台阶时，时间代价翻倍（行李失控风险）
轮椅通行   ：二元判断——路线含 steps（台阶）= 不可达；全 footway = 可达

模型做了一个刻意的简化：不数台阶级数，只算楼层差。因为台阶的高度在校园里基本一致，数级数会引入大量测量噪声， 而楼层差是每个人都能立刻感知、也能用楼层选择器直接验证的量。

1.5 技术实现

  • 纯前端零依赖。HTML5 + CSS3 + 原生 JavaScript，无框架、无第三方库、无 CDN。整个作品就是一个 HTML 文件， 拷到任何一台电脑、用任何现代浏览器打开都能跑，不依赖网络——这一点在决赛现场演示时是实打实的优势。
  • 真实坐标投影成矢量图。用 Python 脚本把 OpenStreetMap 的经纬度按墨卡托变体投影为 SVG 路径 （kx = 1/cos(22.35°)，投影范围以楼栋多边形为准，避免校外道路把地图撑大）， 再用脚本逐层组装成最终页面。地图是矢量图，放大不糊。
  • 分层渲染与绘制顺序。水域 → 绿地 → 遮阴区 → 道路 → 步道 → 台阶 → 建筑 → 路线 → 标记 → 文字，共 15 层， 每一层可以独立开关。
  • 移动端手势。单指拖动 + 双指捏合缩放（0.8×–3.0×）+ 双击复位 + 「复位视图」按钮； 平移量做了夹取，放大后可以拖到任意角落而不会把地图拖出视野。
  • 构建链可复现。12 个脚本按执行顺序编号（抓取 OSM → 提取官方资料 → 投影渲染 SVG → 组装原型 → 美化 → 路线具体化 → 交互优化）， 每一步的输入输出都有文件留痕，换台机器也能重新生成整套地图。

1.6 原创性说明

  • 视角模型是原创的。现有地图产品不区分「同一段路对不同身体条件的人意味着什么」。本作品把 身体条件（能否走台阶）和携带物（拖箱的风险）作为一等公民纳入路径代价，这是作品的主要创新点。
  • 数据采集过程本身是作品的一部分。赛题 FAQ 明确说明「数据采集本身也可以作为作品的一部分」。 作品里的楼层数、出入口位置与朝向、入口有无台阶、电梯通达范围、全程高差、台阶段落， 全部由作者实地步行核实，并据此修正了 OpenStreetMap 的错误数据（图书馆被社区标注为 1 层，实际 4 层）。
  • 端到端自制。从数据采集、几何投影、地图绘制到交互实现，全部自行完成，未使用任何现成地图 SDK 或导航引擎。

2.3 采集与处理方法

  1. 几何数据：通过 Overpass API 按校区 Relation（18704403）与 BBox（22.3500°N–22.3550°N，113.5120°E–113.5190°E）拉取， 过滤出建筑 / 道路 / 步道 / 台阶 / 水域 / 校门六类要素。
  2. 投影：以楼栋多边形为投影范围基准（排除校外道路防止地图被撑大），使用墨卡托变体 kx = 1/cos(22.35°) ≈ 1.083 把经纬度转成 SVG 平面坐标。
  3. 校正：用官方 3D 导览的航拍全景（DJI_0089，22.35243833°N / 113.51640050°E）与官方手册手绘图校正湖面走向、 路线走向与台阶标记；用现场实测数据覆盖 OSM 的楼层与出入口信息。
  4. 成本计算：对每条候选路线沿步道逐段累加水平距离，再按「楼层差 × 1 分钟/层」计入垂直代价，按视角套用惩罚系数。
  5. 验证：作品页的每一个结论都可以在页面上就地核对——把鼠标移到图书馆/台阶上读 tooltip、 打开无障碍视角数一数台阶分布、切换楼层选择器看起点条件怎么变。

三、对比产品分析

我们选择两个已有产品做对照：一个代表「最强大的通用导航」，一个代表「最贴近无障碍议题的专门产品」。 前者说明「主流地图为什么看不见这段距离」，后者说明「看见了一部分，但还差什么」。

3.1 对比对象一：Google Maps / 高德地图（通用导航产品）

它的强项我们承认，并且用到了：全球路网覆盖、实时路况、公交接驳、步行导航、基于大数据的通行时间预测。 这些能力本作品完全没有，也不打算做。

但在校园内部，它有三个结构性盲区：

  1. 把楼外的路网当成全部。这类产品的路径规划在二维路网上寻优——它知道 A 点到 B 点的平面距离， 但不知道你为了走这条路要下 1 层楼。在本校这一段路上，平面距离更短的台阶近路总会被优先推荐， 而「下台阶」这件事在以平面拓扑为核心的数据模型里根本不是一个可比较的量。
  2. 不区分「谁在走」。算法会针对「步行 / 骑行 / 驾车」给出不同结果，但没有「拖着 20 公斤行李的人」 这个模式。而在这条路上，行李恰恰是让推荐结果反转的那个变量。
  3. 室内楼层信息缺失或不可信。主流产品的校园建筑多为一个色块或一个点，楼层、出入口在哪一层、 有没有电梯，基本没有。本作品里的图书馆就是最好的例子：OSM 把它标成 1 层，实际是 4 层，且唯一出入口在 2 层。 这类错误只能靠人到现场才能发现。

3.2 对比对象二：Wheelmap.org / 无障碍地图类产品

它做对的事：把「无障碍」作为一等信息来采集。Wheelmap 这类产品用「完全无障碍 / 部分无障碍 / 不可达」 三档标记地点的轮椅可用性，让轮椅使用者第一次有了可查的信息源。

它的局限也正好是我们要补的：

  1. 标的是「点」，不是「路」。无障碍地图告诉你「这栋楼进得去」，但不会告诉你 「从图书馆到 V27 怎么走才不用上台阶」。而真正让人卡住的往往不是某个门的宽窄，而是一段不得不经过的台阶。
  2. 二元标注，缺少代价。「可达」内部没有代价分档：绕得多远、坡道坡不坡、沿途有没有补给——这些「够不够近」的关键变量没有位置。 而现实中轮椅使用者的决策几乎全在这一档里：不是能不能去，是要多花多少代价去。
  3. 数据依赖众包，更新慢、覆盖不均。校园这类小尺度场景往往没有足够多的标注者。

3.4 结论：主流产品算的是「最短」，我们算的是「最近」

把两条路线放在一起看，这个差别就很具体了：

537 m路线 A 实测距离 —— 预设中的「近路」，实测反而更长
−1 层路线 A 的隐藏高差 —— 拖箱的人是风险，轮椅的人是墙壁
470 m路线 B 实测距离 —— 「绕行路」实测更短更快
三种推荐同一组数据得出的答案 —— A / B / B

主流地图产品处理「最短」，是因为它的数据模型里只有平面这一维，这是模型层面的盲区，不是算法不够好。 无障碍产品处理了「能不能」，但还没处理「代价多少」。 本作品想说的是：把「谁在走」当成路径规划的一等输入，那段看不见的距离就显现出来了—— 它可能是 1 层楼的高差，可能是拖箱时的一次失控，也可能是轮椅面前一道过不去的台阶。

作品最想留下的一句话：同一段路，三种人生，三种「最近」。地图上的最短，从来就不等于你脚下最近的那条。

四、核心设计决策与技术取舍

赛题要求说明核心设计决策与技术取舍。以下六组决策，每一条都写清「为什么不是另一种做法」。

4.1 零依赖单文件 HTML，而不是框架 + 构建链

作品是一个不引用任何外部资源的单文件 HTML（无 CDN、无字体包、无图标库、无 JS 框架）。 理由：演示环境的网络状况不可控，任何外部依赖都是现场翻车点；单文件意味着拷到任何一台电脑、断网也能完整运行。 代价是代码体积集中在一份文件里、可维护性下降——我们用 脚本/verify_page.py 的 33 条自动化回归断言来对冲这一代价。

4.2 量化口径「只算楼层差，不数台阶」

台阶的级数既没有可靠来源，也随路线记录粒度变化，把级数当变量会让结论不可复现。 我们把口径收敛为「楼层高差 × 基准时间」：图书馆（4 层，出入口在 2F）→ V27（7 层，1F 入口）全程净高差 −1 层， 这一数字可以现场步行核实，是稳定的。 代价是无法区分「3 级台阶」和「30 级台阶」——因此作品明确声明：结论基于有限次现场查看，不构成无障碍通行保证。

4.3 OSM 坐标打底 + 一手核实修正，而不是全信或全弃

OpenStreetMap 的楼栋轮廓与步道走向是现成的、坐标级的底料，放弃它等于凭空画地图； 但它的社区标注并非全对——例如本例中 OSM 把图书馆标为 building:levels=1，而现场核实是 4 层。 我们的取舍：轮廓/步道用 OSM，与可达性相关的关键字段（楼层、出入口、有无台阶、电梯）全部以现场实测为准， 并把「哪些字段来自哪里」写进作品页的数据真实性分级表。

4.4 三视角对比，而不是通用无障碍路径规划引擎

引入完整的 routing 引擎（OSRM / Valhalla 等）可以算任意起终点的无障碍路径，但会把作品变成「另一个导航产品」， 而赛题问的是「为什么最短不等于最近」这个认知问题。 我们选择把一条路讲透：同一组数据，在「普通行人 / 拖行李 / 轮椅」三种身份下输出三种不同推荐（A / B / B）， 用反转本身来说明盲区。代价是覆盖面只有一段示例路线，这一点已在对比产品分析中如实标注。

4.5 湖岸线用虚线示意，而不是实心精确多边形

几何自检发现：中心湖的岸线多边形与 16 条真实 OSM 步道、6 段台阶的坐标存在压盖，说明岸线形状本身不可靠。 我们不画实心湖面，改用虚线示意岸线并标注「岸线示意」——在拿到实测轨迹前，不假装比数据更精确。 这是本作品「数据诚实性优先于视觉完成度」原则的一个具体体现。

4.6 把「命题 / 方法 / 结论」写进作品页正文

本赛道的预选由 AI Agent 按评审规则打分，Agent 读到的就是作品页本身——所以作品页首屏就有结构化的 「命题（最短 ≠ 最近）→ 方法（真实坐标 + 现场实测 + 三身份量化）→ 结论（实测 537 m vs 470 m，推荐 B / B / B，室内路线 C 采集中）」陈述， 核心数字在页面正文前 400 字内可读，而不是埋在提交材料里。
