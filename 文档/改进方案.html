最紧急的一件事：作品违反了赛题明确写出的禁止条款。
赛题《内容与安全边界》原文：「涉及路线和空间的作品，不得声称某条路线绝对安全或完全无障碍。」
而当前作品里有多处这样的表述：「推荐路线 B（唯一可行）」「路线 B 是唯一选择」「全平路，无台阶，轮椅友好」。 这些都属于对无障碍性的承诺性表述。预选由 Agent 按规则打分，这类违规是最容易被直接抓到的扣分点，而且改动成本极低（改文案 + 加免责声明）。
最大的机会：题目原文其实已经把「看不见的距离」拆成了四类，作品只做了其中一类。
题目《背景》段落列举了四种情形：① 不停寻找入口和方向；② 看似很近却总在关键时刻被挡住； ③ 沿途可以补给和休息；④ 一旦出发就只能硬着头皮走完。
当前作品完整覆盖了 ②（台阶造成的物理阻断），但 ①③④ 都还没做。 其中 ① 的量化只需要接一根线——因为「图书馆唯一出入口在 2F」这条你已经现场核实的数据， 本身就是「不停寻找入口」的完美案例，而它现在只是页面上一段说明文字，没有进入代价模型。

3扣题深度：题目原文四个痛点 vs 当前覆盖

赛题《背景》原文这一段，实际上已经把这题想探索的方向列全了：

「有的路需要不停寻找入口和方向，有的路看似很近，却总在关键时刻被挡住；
有的路沿途可以补给和休息，有的路一旦出发，就只能硬着头皮走完。」
#原文痛点本质当前覆盖可用的现成素材
① 需要不停寻找入口和方向 认知成本 / 寻路难度 未覆盖（只有文案提示） 图书馆唯一出入口在 2F。从 1F 进去的人找不到出口，必须上到 2F——这条你已现场核实，而且楼层选择器已经做出来了，只差接进代价模型
② 看似很近，却总在关键时刻被挡住 物理阻断 已覆盖（核心） 台阶导致的轮椅不可达、拖箱风险
③ 沿途可以补给和休息 沿途资源 / 恢复点 未覆盖 需要一次现场采集：饮水点、座椅、遮阴、便利店、卫生间
④ 一旦出发，就只能硬着头皮走完 不可逆性 / 退出成本 未覆盖 台阶下到一半无法回头；在台阶口之前存在「最后折返点」，可量化「过了这个点，改走 B 要多花多少」
为什么这比加新功能更重要：赛题的建议是「从一个具体、真实、你们自己熟悉的场景出发，切口小一些，把一件事做完整」。
所以正确方向不是扩到更多路线对（那会稀释切口），而是把同一条路线上的「看不见」挖得更深—— 在同一段路上同时呈现四类成本，让「最短 ≠ 最近」这个论点从「一个理由」变成「一组理由」。 这会显著提高扣题分，且几乎不需要新的外部数据（①④ 都能用已有数据算出来，只有 ③ 需要去现场）。

5P1 · 高性价比（直接提升竞争力）

P1-1 把「出发楼层」接进代价模型 ★ 本次方案里价值最高的一项

依据：题目原文「有的路需要不停寻找入口和方向」；扣题要求「可用于比较和选择」

现状：楼层选择器已经做好，但 FLOOR_DATA 里全是文案字段，没有任何数值，renderFloor() 只改卡片文字和高亮建筑。也就是说——「你从几楼出发」这个条件目前完全不影响路线代价，楼层选择器是一个孤立的展示组件。

为什么这件事特别值得做：「图书馆唯一出入口在 2F」是你现场核实的一手数据。 它造成了一个地图完全看不见的现象——你以为从图书馆 1F 出发很近，但你根本出不去，得先上到 2F 找那个唯一的出口。 Google Maps 不知道图书馆 1F 没有出口。这就是题目原文说的「不停寻找入口和方向」。 把这条数据接进模型，等于用你已有的数据覆盖了题目四分之一的方向，边际成本极低。

改法（分三步，可独立验证）

第 1 步：给 FLOOR_DATA 加数值字段

'lib-1': {
  title: '图书馆 1F', status: 'status-warn', statusText: '无直接出入口',
  desc: '…',

},
'lib-2': { …, preFloorDelta: 0, preAction: '直接出门', preNote: '唯一出入口层，无需额外移动' },
'lib-3': { …, preFloorDelta: -1, … },   // 下到 2F
'lib-4': { …, preFloorDelta: -2, … },
'v27-7': { …, postFloorDelta: -6, postAction: '乘电梯下到 1F 出口' }   // 到达后

第 2 步：把楼层调整加进总代价

var MIN_PER_FLOOR = 1;        // 每层耗时（分钟）—— 同时也是 P1-3 参数面板要暴露的旋钮
var ELEVATOR_FACTOR = 0.4;    // 电梯折算系数（走楼梯 = 1.0）
                              // ⚠️ 这个 0.4 是假设值，必须在页面上标注为「假设」

function floorCostMinutes(delta, hasElevator) {
  return Math.abs(delta) * MIN_PER_FLOOR * (hasElevator ? ELEVATOR_FACTOR : 1);
}

// 总时间 = 出发楼层调整 + 路线本身 + 到达楼层调整
totalTime(view) = floorCost(libFloor) + VIEWS[view].time[route] + floorCost(v27Floor);

第 3 步：让表格与条形图实时反映

在 renderView() 里读取当前楼层选择器的值，重算「本层出发」这一行的数字；并在表格上方加一行提示，例如：

从图书馆 1F 出发：需先上 1 层到 2F（+1 分钟），全程 5 分钟。
地图上看不出这一点——1F 没有通往户外的门。

改完会新增的对比结论（对扣题极有价值）

出发楼层必须先做路线 A 总时间路线 B 总时间推荐是否改变
图书馆 2F（唯一出口层）无需额外移动4 分钟6 分钟普通行人 → A
图书馆 1F上 1 层找出口5 分钟7 分钟不变，但差距被放大
图书馆 4F下 2 层到 2F4.8 分钟（电梯）6.8 分钟（电梯）不变

更重要的推论：如果你已经在 V27 7F，反过来要去图书馆，这条「楼层成本」会反向放大——而这一类「反向出行的不对称」正是地图从不告诉你的东西。 可作为下一步扩展（见 P2）。

工作量：约 4–6 小时（含 UI 调整与测试）

风险：电梯系数 0.4 是假设值 → 必须在页面上明示为「假设参数」，或直接在 P1-3 的参数面板里暴露成第三个旋钮

验收：切换楼层选择器时，「预估时间」一栏的数字必须随之变化；且在图书馆 1F 时能看到「需先上 1 层」的提示

P1-2 加「最后折返点」，覆盖「不可逆性」维度

依据：题目原文「有的路一旦出发，就只能硬着头皮走完」

现状：完全没有涉及。「拖箱下台阶有风险」只说了风险，没说发现得晚就来不及了。

设计

  1. 在路线 A 上、台阶开始之前的位置标一个「最后折返点」标记（沿用现有 .guide-dot 交互样式，加一个不同颜色）。
  2. 点开弹窗，给出这段算式的结论：
    最后折返点
    过了这里，路线 A 只剩台阶，没有岔路。
    在此处改走 B：多走约 150 m（约 2 分钟）。
    在台阶下到一半时改走 B：需先爬回 −1 层，再绕行，约 5 分钟。
    拖箱的人在这个点上做的决定，代价差一倍。
    （上方数字为示意。150 m 可直接由 450 m − 300 m 得出；两类改道耗时需按路线坐标分段累加后填实际值， 不要直接抄这组示意数字。）
  3. 在对比表里加一栏「决策可逆性」：路线 A 写「仅台阶前可改道」，路线 B 写「全程可改道」。

为什么这个改动划算：不需要任何新数据（所有距离都能从现有路线坐标算出来）， 但把「风险」从形容词变成了一个带数字的决策——这正是赛题要的「可以衡量、用于选择」。

工作量：约 3 小时

P1-3 路线参数面板：让观众亲手把结论拧反

依据：「让它可以被观察、衡量，并用于比较和选择」；决赛由观众投票，观众上手体验

设计

在「路线对比」卡片顶部加两个滑块（第三个可选）：

旋钮范围默认拧动时会发生什么
每层楼梯耗时0.5 – 2.0 分钟1.0影响所有含高差的路线
拖箱惩罚倍数1.0 – 3.0 倍2.0降到 1.2 以下时，拖行李的推荐会从 B 翻回 A
电梯折算系数0.2 – 1.00.4影响 P1-1 的楼层成本（做了 P1-1 才需要）
这一项一箭三雕：
① 把「1 分钟/层是拍脑袋定的」这个尴尬变成卖点——不再是「我们的假设没依据」，而是「我们展示结论对假设的敏感性」， 并告诉观众「当惩罚系数低于 1.2 时，反转就消失了」。这是学术上更强的表述。
② 与 Google Maps 的核心差异被具象化：主流地图的推荐是黑盒，我们的推荐可以被观众亲手拨动、看到结论在哪个点翻转。
③ 解决了「现场无法即兴演示」的问题——评委问「系数怎么定的」，直接拉给他看。

实现要点

  • 把 VIEWS 里写死的 time / dist 拆成「基础量」+「系数」，由 recalcAll() 统一重算。
  • 重算后同步更新：表格、三个条形图、徽章（推荐路线可能翻转）、以及 P1-1 的楼层成本。
  • 翻转时给出醒目提示：「在当前的系数假设下，拖行李的推荐已翻转为路线 A。」——这个瞬间就是全场最值得看的一秒。
  • 面板里保留一句「本面板参数为可调假设，非实测值（实测方法见提交材料）」，避免违反模拟数据标注要求。

工作量：约 6–8 小时（建议在 P1-1 之后做，两者共用重算逻辑）

P1-4 加「现场核查记录」，把数据采集变成作品的一部分

依据：赛题明确说「数据采集本身也可以作为作品的一部分」；且预选由 Agent 打分，需要可核查的证据

设计

在「数据来源」区块里加一张小表：

核查项OpenStreetMap 原始值现场核查值核查方式
图书馆层数1 层4 层逐层步行 + 电梯楼层编号
图书馆出入口无记录唯一出入口在 2F，朝东南（湖侧），无台阶绕楼一周确认
图书馆电梯无记录全楼层互通（1F–4F）实际乘坐确认
V27 入口无记录楼体拐弯处，无台阶，电梯通达全楼层绕楼一周确认
全程高差无记录（海拔 API 返回屋顶高度，方向相反，不可用）−1 层（下坡）步行实测

最后一行的「海拔 API 方向相反」值得写进去——它说明你尝试过自动化方案、发现不可靠、才改为人工实测，这是技术判断力的直接体现。

工作量：约 1.5 小时（含把「待核」状态一并展示：40 栋楼楼层数来自 OSM 未核实）

P1-5 首屏加「30 秒叙事」，面向观众投票

依据：决赛「由观众投票给出最终评分」「评委必须允许上手体验」——观众不是专家

现状：页面一打开就是地图 + 数据表，工具感强、叙事感弱。非专业观众很难在 30 秒内明白这个作品「厉害在哪」。

设计（三种，按成本从低到高）

方案做法成本
A · 一句话钩子（推荐先做） 在 P0-3 那张「命题」卡片里，把赛题问句做成大字标题，下面紧跟一句最扎心的对比：
同样 300 m 的路，拖着一个 20 公斤的箱子，它就从「最近的」变成了「最危险的」。

6P2 · 加分与收尾

P2-1 沿途补给与休息点采集 （覆盖第四个痛点，需一次现场）

依据：题目原文「有的路沿途可以补给和休息」

沿路线 A 与 B 各走一遍，记录：饮水点、座椅、遮阴段（有盖连廊）、便利店、卫生间。在地图上用小图标标出两条路各自的数量，并在对比表加一行「沿途可休息点」。

这是四个痛点里唯一还需要现场采集的。采一次约 30 分钟，能补齐整个论点拼图的最后一块。遮阴数据现在已有建筑资料依据（Ronald Lu & Partners），可以直接复用。

P2-2 反向出行：从 V27 去图书馆

同一段路反过来走，成本结构会变（现在是从 −1 层的下坡变成上坡；从 V27 7F 出发要先下到 1F）。 这能证明「看不见的距离」不只是路线问题，还和朝向与起点条件有关。

成本：约 3 小时（复用现有路线几何，只是反向 + 重算符号）。价值：让「不对称性」成为第二个论点。但注意别让切口变大——只做这一对反向即可。

P2-3 移动端真机测试

决赛评委很可能用手机上手。需要真机验证：手势缩放是否跟手、底部导航是否挡住内容、地图在小屏上的可读性。

成本：1 小时（需要一台真手机）。目前只在无头浏览器里验证过 1500px 宽度的桌面视图。

P2-4 演示视频（30–45 秒）

决赛 presentation 用。建议按这个节奏剪：地图全景（5s）→ 勾选路线，两条路出现（8s）→ 切「拖行李」，A 变灰 B 变绿（10s）→ 切「轮椅」，A 显示不可达（8s）→ 参数面板拧一下，结论翻转（10s）。

最后那 10 秒是全场最值得展示的内容，所以建议先做 P1-3 再录视频。

8不建议做的事

赛题明确建议「切口小一些，把一件事做完整，往往比做一个大而全的系统更有说服力」。以下方向看起来诱人，但会稀释切口或违反规则：

不建议原因
扩展成全校园多路线导航 题目反复强调「一栋楼、一段路线就够」；且 40 栋楼的楼层数据未核实，扩得越大错误越多
接入真实地图 SDK 作底图 赛题明说「单纯调用地图服务计算最短路径不足以回答这道题」；还会丢掉「零依赖离线可演示」这个现场优势
加登录 / 后端 / 用户系统 与本命题无关；且引入隐私合规问题（赛题对个人信息有专门条款）
为「AI Track」而硬塞一个 AI 功能 规则并不要求作品调用 AI；硬塞会破坏离线稳定性。正确做法是诚实声明没用 AI，并说明这是取舍（已列入 P0-4）
把无实测依据的系数包装成精确值 一旦被追问就是减分项。改为 P1-3 的可调参数 + 敏感性展示，反而变成加分项
对具体楼栋下「无障碍」结论 直接违反安全边界条款。只描述「本次查看是否发现台阶」，不下可达性结论

9验收清单

合规验收（P0，逐条勾选）

  • ☐ 全页搜索「唯一可行 / 唯一选择 / 轮椅友好 / 完全阻断」→ 结果为空或已改为限定表述
  • ☐ 页面存在明确的「使用限制 / 免责声明」，包含「未测量坡度、路面宽度」与「不构成无障碍通行保证」
  • ☐ 打开页面即可看到两条路线（无需任何点击）
  • ☐ 去掉 script/style 后取纯文本，前 400 字内能读到「命题 / 方法 / 结论」与核心数字
  • ☐ 作品页底部有相近产品对比（至少 1 个）
  • ☐ 提交材料包含：技术取舍、开源与既有物料声明、AI 使用说明（含「不调用 AI 模型」的明确说明）
  • ☐ python3 脚本/verify_page.py 全绿

扣题深度验收（P1）

  • ☐ 切换出发楼层时，预估时间数字随之变化（P1-1 打通）
  • ☐ 地图上存在「最后折返点」标记，点开有改道代价数字（P1-2）
  • ☐ 拖动参数滑块时，表格 / 条形图 / 推荐徽章同步更新；把拖箱惩罚降到 1.2 以下时推荐翻转为 A（P1-3）
  • ☐ 页面能读到「数据采集过程」，包含 OSM 原始值 vs 现场核查值的对照（P1-4）
  • ☐ 四类「看不见的距离」（寻路 / 阻断 / 补给 / 不可逆）至少覆盖 3 类（P1-1、P1-2、P2-1）

现场演示验收

  • ☐ 断网状态下双击 作品/index.html，所有功能正常
  • ☐ 用手机打开，手势缩放跟手，底部导航不遮挡关键内容
  • ☐ 让一个没看过这个作品的人自己操作 60 秒，能说出「同一段路对不同人结论不同」
最后一句判断：这个作品的技术底座已经够扎实了（真实数据、自建代价模型、零依赖离线可演示）， 真正拉开差距的是两件事—— 一是把已有的数据用满（「图书馆 1F 出不去」这条你辛苦核实的数据，现在还只是一段说明文字，没进模型）； 二是让评审能读懂（预选是 Agent 打分，页面上的文字就是答卷）。 这两件事都不需要新数据，属于「已经付了成本但还没兑现收益」的部分。
