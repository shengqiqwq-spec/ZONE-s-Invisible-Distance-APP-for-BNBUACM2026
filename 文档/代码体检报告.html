一句话结论：作品的地图数据、量化模型和交互设计都站得住，但代码里有一批「看起来能用、实际点了就坏」的开关。 最致命的是切换到「拖行李 / 轮椅」视角会把地图上的路线和无障碍高亮全部清掉——而这三个视角的对比恰恰是整个作品的灵魂。 这类问题在决赛现场演示时最容易翻车，已经全部修掉并跑通回归测试。

一、致命问题（已修复）

致命 1. 切视角会清空地图状态，路线和无障碍高亮整体消失

原代码在切换视角时执行的是：

svg.setAttribute('class', 'view-' + view);   // 整体覆盖 class 属性

setAttribute 是替换而不是追加，于是「路线」开关加的 routes-visible、「无障碍视角」加的 mode-access 被一并抹掉。复现步骤（原版必现）：

  1. 勾选地图工具栏的「路线」→ 两条路线出现 ✓
  2. 点上方「拖行李」→ 路线全部消失，但复选框仍然是勾选状态 ✗
  3. 点「轮椅 / 无障碍」→ 台阶高亮同样消失 ✗

修法：引入一个状态对象统一管理 class，每次拼装而不是覆盖。

var svgState = { view:'walker', routes:false, access:false, floorActive:false };
function applySvgClass() {
  var cls = ['view-' + svgState.view];
  if (svgState.routes)     cls.push('routes-visible');
  if (svgState.access)     cls.push('mode-access');
  if (svgState.floorActive) cls.push('floor-active');
  document.getElementById('campusMap').setAttribute('class', cls.join(' '));
}

全部写 class 的地方现在只走这一个出口，三个开关可以任意叠加、互不干扰。

致命 2. 「楼层高差」条形图把下坡 -1 层 显示成 +1 层

表格里写的是「-1 层（下坡省力）」，紧邻下方的条形图却标成「+1层」——同一个面板里自己打自己。 原因是数据里存的是绝对值 floor: [1, 0]，显示时又套了一层「大于 0 就加 + 号」的逻辑。

修法：把符号信息保留在数据里，绝对值只用于条宽。

floor: [-1, 0],      // 显示用：保留正负号
floorBar: [1, 0]     // 条宽用：取绝对值

现在三个视角都正确显示「-1层 / 0层」，与表格、脚注、弹窗文案完全一致。

二、严重问题（已修复）

严重 3. 楼层切换的楼栋高亮是死代码

CSS 里写了 .floor-active #bld-library 和 .floor-active #bld-v27，但 SVG 里没有任何元素带这两个 id （42 栋楼只有 class 和 data-name）。所以「选择图书馆 3F」时，本该闪蓝光高亮的图书馆其实一点反应都没有， 而这个高亮正是「楼层选择器」这个功能唯一的视觉反馈。修法：给图书馆和 V27 的轮廓补上 id。

严重 4. 图书馆楼层自相矛盾：正文说 4 层，鼠标一悬停显示 1 层

正文、脚注、数据来源都写明「图书馆 4 层（OSM 标 1 层有误，已现场核实）」，但图书馆轮廓的 data-name 里仍然是 OSM 的原始值「· 1 层」。评委把鼠标移到地图上的图书馆，看到的就是被作品自己否定的那个错误数字。 修法：tooltip 文案改为「4 层 · 唯一出入口在 2F 朝东南（现场核实）」，并加上 data-levels="4" 便于脚本读取。

严重 5. 鼠标滚轮被劫持：停在图上滚页面变成了缩放地图

container.addEventListener('wheel', function(e) {
  e.preventDefault();          // 无条件吞掉所有滚轮事件
  scale = ...;
}, {passive:false});

地图占了页面的绝大部分，鼠标只要停在图上就再也滚不动页面了。在 macOS 触控板上尤其难受——两指滑动本来是滚动， 结果一直在缩放地图。修法：只有按住 ⌘／Ctrl 时才缩放（触控板捏合手势本身会带 ctrlKey）， 普通滚动交还页面。另外补了「复位视图」按钮和双击复位。

严重 6. 双击复位会被捏合、拖动误触发

原代码把双击检测挂在 touchend 上，且不判断这一指是不是「轻点」： 

container.addEventListener('touchend', function(e) {   // 任何手指抬起都算一次
  if (now - lastTap < 300) { scale = 1; tx = 0; ty = 0; }
});

后果：捏合缩放时先松一根手指 → 记一次；再松另一根 → 300ms 内判定为双击 → 缩放被复位。 在地图上拖完一段再抬手同样会误复位。修法：记录位移量，只有「未移动 + 非捏合 + 最后一根手指抬起」才算轻点。

严重 7. touch-action 与 JS 手势互相打架，缩放后看不到被裁掉的部分

SVG 上写了 touch-action: pan-x pan-y pinch-zoom（交给浏览器原生手势），父容器又设了 overflow:auto，同时 JS 还在 touchmove 里 preventDefault() 自己实现缩放。 三方抢同一个手势，结果是抖动、双重缩放。 另外 transform 不改变布局尺寸，缩放 2 倍后地图边缘超出容器但无法滚动看到，等于放大了也没用。 修法：容器改 overflow:hidden、SVG 改 touch-action:none，手势全部由 JS 接管， 并给平移量加夹取，既不会把地图拖飞，放大后也能拖到任意角落。

三、中等问题（已修复）

中等 8. 「中心湖」根本看不见，「中心岛」从来就没显示过

这是本次体检里最值得说的一条——一个视觉 bug 掩盖着另一个视觉 bug。
  • 湖：湖泊路径的填充色是 #eef3ea，和画布背景色完全相同，等于用背景色把湖涂掉了。 地图上只剩一个「中心湖」文字标签和一条孤零零的棕色栈道线。
  • 岛：中心岛多边形的坐标落在图书馆轮廓内部，而建筑是在湖之后绘制的， 所以岛被图书馆整个盖住——这个元素从做出来那天起就没被看见过。只有它的文字标签（标签绘制在最上层）浮在图书馆上面， 于是地图上出现了一个「飘在图书馆楼顶上的『中心岛』标签」。

我做的处理（为什么不直接"补一片好看的湖"）：我把湖的填充改成了淡蓝色虚线示意岸线，标注文字改成「中心湖（岸线示意）」， 并把中心岛和栈道移到示意湖面的开阔处，让「湖—栈道—岛」三件套终于读得通。

但我不敢把它画成实心精确湖面，原因是有实测依据的：我写脚本做了点在多边形内的几何自检， 发现现有这个湖岸线多边形压住了 16 条真实 OSM 步道和 6 段台阶的坐标点。也就是说这个多边形的形状/位置本身就不准， 大概率就是原作者发现穿模之后，选择用背景色把它涂掉、而不是去改坐标。 在没有真实湖岸数据之前，画成实心只会制造一处更显眼的错误地理信息；画成虚线示意则在视觉上说得通、又不冒充实测。

要真正修好，需要：中心湖岸线的实测轨迹（沿湖走一圈用手机 GPS 记录即可），或校方总平面图上的精确岸线。已列入待办。

中等 9. 无障碍模式下水域不会淡出（选择器 class 名不一致）

.mode-access .lyr-water 只选得中校园东侧的湿地，选不中湖（class 是 lyr-lake）。 已把 .lyr-lake 加进选择器，与其余底图图层一起淡出到 25%。

中等 10. 9 处楼栋标注是空的，悬停会弹出一个空白黑框

SVG 里有 5 处 data-name=""（完全空），另有 4 处残名只写了一半，形如 data-name=" · 4 层"。 原代码 tip.textContent = el.dataset.name || '' 不判空，鼠标划过去就弹一个只有背景色的空浮层。 已统一补成「未命名建筑（OSM 未标注名称）［· N 层］」，并在 hover 处理器里加了 if (!name) return; 兜底。

中等 11. 独立地图侧栏有 11 条空白条目

地图/校园地图.html 的「大型设施」列表里有 11 行是 <li><b></b><span></span></li>， 渲染出来就是一串空行。已改为有名称的条目 + 一条「未命名建筑 × 11」的汇总说明， 同时把图书馆楼层从 1 层改正为 4 层，并补上数据分级与模拟数据声明。

中等 12. 缺了赛题硬性要求的「模拟数据标注」

赛题 FAQ 白纸黑字写着：「涉及真实校方系统的部分需标注哪些是模拟数据。」原作品全文没有任何一处做这个区分， 这属于评审会直接扣分的合规项。

已在作品页「数据来源」区域补了一张数据真实性分级表（现场实测 / 开源地图 / 官方资料 / 示意模拟 / 待核）， 并加了一段明确的模拟数据声明：标注为「示意」的（中心岛轮廓、遮阴连廊范围、路线长度、时间系数） 均为推断或经验值；作品未接入任何校方真实业务系统，不读取、不写入学校数据库，全部数据以静态文件内置。

六、尚未修复：这 5 件事需要你（或现场数据）拍板

#事项为什么我没动
待你定 扩展更多路线对（T7→食堂、V20→体育馆、西门→图书馆等） 需要新数据。要哪几条路线、每条走哪种出行视角，得你先定。定下来我可以照现在的量化模型批量做。
需实测 路线长度未 GPS 实测（现在 300m/450m 是步道坐标累计的估算值） 只有你能走一遍。手机装个轨迹记录 App，沿两条路各走一次即可，我可以写脚本把 GPX 转成图上的折线。
需实测 其余 40 栋楼的楼层数直接沿用 OSM，未现场核对（图书馆已经错了一次，说明这个数据源不可靠） 要一栋一栋看。建议按「你去得最勤的 5 栋」优先，我可以把清单列成一页对照表方便你边走边填。
需实测 湖岸线、中心岛、遮阴/连廊范围没有真实几何 见第 8 条。现在用虚线示意画法兜住，不算错但也不算对。
待你定 时间系数是经验值（每层 1 分钟、拖箱惩罚 2 倍） 这两个数是整个量化模型的支点，目前没有任何实测支撑。要不要换成「拖箱 1.5 倍」或给个区间，你定。
另外提一句风险：作品是纯静态单文件，所有路线数据写死在 HTML 里。现场演示没问题、很稳（零依赖、不联网、不怕断网）， 但如果评委问「能不能加一条新路线，现在加给我看」，就没法即兴改。要不要做一个极简的「路线参数面板」放在页面上（改系数即时重算）， 这是决赛现场最能加分的东西之一——你说了我就做。
